## 1. 产品定位与目标

### 1.1 一句话定位
Talk2ESP 是一款通过自然语言对话即可全自动完成 ESP32 单片机开发（编码→编译→烧录→验证）的桌面工具。

### 1.2 核心价值主张
- 用户只需接好开发板与外设、用自然语言描述需求，AI 即可完成从代码生成到烧录验证的全流程；
- 全过程可追溯、可配置、有安全护栏，让创客/爱好者专注「想法」而非「工具链折腾」；
- 基于 esptool + arduino-cli 的轻量化工具链，环境简单、体积小巧、开箱即用。

### 1.3 设计目标
1. **全自动闭环**：需求→代码→编译→烧录→验证，失败可自动重试（上限 3 次），超限转人工；
2. **轻量化**：esptool + arduino-cli，环境简单、体积小巧，契合「开箱即用」理念；
3. **安全可控**：引脚黑名单、危险代码告警、烧录前确认、敏感数据加密四道护栏；
4. **可扩展**：芯片型号（S3/C3 起步）、LLM 供应商、外设能力均可扩展；
5. **可追溯**：每个项目以文件夹形式留存对话记录、代码、编译/烧录/验证日志。

### 1.4 非目标（v1 不做）
- 不做 IDE 插件集成、不做云端部署、不做 Web 端形态；
- 不做离线本地大模型支持（在线为主）；
- 不做示波器/逻辑分析仪等硬件级可视化分析；
- 不做 ESP-IDF 框架支持（v1 仅 Arduino）；
- 双板互连测试环境仅用于 Talk2ESP 自身开发自测，不作为产品功能暴露给终端用户。

### 1.5 目标用户
| 优先级 | 用户群 | 诉求 | Talk2ESP 的应对 |
|---|---|---|---|
| 主要 | 创客/爱好者 | 有基础电子与编程知识，想快速把想法落地 | 清晰可控的全自动流程，能看懂代码与外设接线 |
| 次要 | 嵌入式初学者/学生 | 零基础，需手把手引导 | 更高自动化默认 + 详细错误解读 |
| 次要 | 专业工程师 | 快速原型验证，关注效率与可控性 | 可切换分步确认模式，可直接编辑生成代码 |

## 2. 功能范围与用户流程

### 2.1 核心功能模块

| 模块 | 职责 | v1 范围 |
|---|---|---|
| **AI 对话** | 多轮对话澄清需求、生成需求确认书、生成代码、诊断错误、判定验证结果 | OpenAI/Claude/国产模型可切换 |
| **需求确认书** | 结构化输出（型号/外设/引脚/预期行为/测试桩预期），用户确认后才生成代码 | v1 必备 |
| **代码生成** | 生成 Arduino 原生代码 + 测试桩代码，遵循引脚黑名单 | v1 必备 |
| **设备管理** | 自动扫描串口、识别型号（USB PID/VID 或芯片 ID）、手动修正、多设备并行 | v1：S3/C3 |
| **编译** | 内置 arduino-cli，自动管理 arduino-esp32 核心包与依赖库 | v1 必备 |
| **烧录** | esptool 烧录，烧录前确认（型号/串口/代码摘要） | v1 必备 |
| **串口监控** | 烧录后自动打开，实时显示 + 可手动发送数据 | v1：可读可发 |
| **闭环验证** | AI 读串口输出匹配测试桩关键字（如 `TEST:PASS`）判定通过/失败 | v1 必备 |
| **失败自愈** | 编译/烧录/验证失败，AI 分析错误自动修复，重试上限 3 次 | v1 必备 |
| **项目持久化** | 每项目一文件夹（.ino + 依赖 + 对话记录 + 各阶段日志），可导入导出 | v1 必备 |
| **示例库** | 内置常用示例（LED/按键/I2C/SPI/PWM/串口等），AI 生成可参考、用户可套用 | v1 必备 |
| **设置** | LLM 供应商/Key、自动化模式、引脚黑名单、路径配置 | v1 必备 |

### 2.2 主用户流程（流水线编排）

```
[1] 设备准备    用户接好开发板+外设，启动 Talk2ESP
       ↓
[2] 设备发现    自动扫描串口 → 识别型号 → 用户确认/修正
       ↓
[3] 需求对话    用户输入需求 → AI 多轮澄清 → 输出【需求确认书】
       ↓                                        （含型号/外设/引脚/预期行为/测试桩预期）
[4] 用户确认    用户审阅需求确认书 → 确认/修改
       ↓
[5] 代码生成    AI 生成 .ino + 测试桩代码（校验引脚黑名单/危险操作告警）
       ↓
[6] 编译        arduino-cli 编译 → 失败则 AI 诊断修复重试(≤3次)
       ↓
[7] 烧录前确认  显示型号/串口/代码摘要 → 用户确认（全自动模式可配置跳过）
       ↓
[8] 烧录        esptool 烧录 .bin → 失败则 AI 诊断重试(≤3次)
       ↓
[9] 串口监控    自动打开监控，运行测试桩，实时显示输出
       ↓
[10] 验证判定   AI 读串口匹配测试桩关键字 → 通过/失败
       ↓                                         失败则 AI 诊断修复重试(≤3次)
[11] 结果呈现   通过：归档项目；失败超限：转人工，保留全流程日志
```

### 2.3 自动化模式（可配置）
- **全自动模式**：步骤 [5]→[10] 连续执行，仅保留 [7] 烧录前确认（可配置关闭，默认开）；
- **分步确认模式**：每个关键步骤（[4][5][6][7][8][9][10]）都需用户确认后才继续。

### 2.4 失败处理统一策略
- 每个可失败阶段（编译/烧录/验证）独立计数重试，上限 **3 次**；
- 每次重试由 AI 读取错误/串口输出 → 分析 → 修改代码或参数 → 重新进入该阶段；
- 重试耗尽转人工，保留完整日志与最后一次错误，用户可手动接管或修改需求重开。

## 3. 架构设计（方案 A：流水线编排式）

### 3.1 分层架构

```
┌─────────────────────────────────────────────────────┐
│  前端层 (Web: React/Vue + Tauri WebView)             │
│  对话UI · 设备列表 · 串口监控 · 项目管理 · 设置       │
└────────────────────┬────────────────────────────────┘
                     │ Tauri IPC (invoke/event)
┌────────────────────┴────────────────────────────────┐
│  应用层 (Rust)                                       │
│  ┌──────────────────────────────────────────────┐   │
│  │ Pipeline Orchestrator (状态机编排核心)        │   │
│  │  需求澄清→确认→代码生成→编译→烧录→验证→归档  │   │
│  └──────────────────────────────────────────────┘   │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌──────────┐  │
│  │AI 适配层│ │工具链层 │ │设备/串口│ │项目/存储 │  │
│  │(多供应商)│ │(cli/   │ │ 层      │ │ 层       │  │
│  │         │ │esptool)│ │         │ │          │  │
│  └─────────┘ └─────────┘ └─────────┘ └──────────┘  │
└────────────────────┬────────────────────────────────┘
                     │
┌────────────────────┴────────────────────────────────┐
│  能力层 (外部进程/系统)                              │
│  arduino-cli · esptool · 串口驱动 · LLM HTTP API     │
└─────────────────────────────────────────────────────┘
```

### 3.2 核心组件职责

**Pipeline Orchestrator（流水线编排器，Rust）**
- 维护项目状态机：`Drafting → Confirmed → Coding → Compiling → FlashingConfirm → Flashing → Verifying → Archived / Failed`；
- 按状态推进，调用各能力层；不把流程控制权交给 AI；
- 记录每阶段输入/输出/耗时/日志到项目文件夹；
- 实现失败重试计数与超限转人工。

**AI 适配层（LLM Adapter）**
- 统一抽象：`chat(messages) → response`、`generate_code(spec) → code`、`diagnose(error) → fix`、`judge(serial_output) → verdict`；
- 适配器模式支持多供应商（OpenAI/Claude/国产），Key 加密存储；
- AI 仅在被编排器调用时发挥能力，不直接调用工具链。

**工具链层（Toolchain）**
- `arduino-cli` 封装：核心包/库安装、编译、产出 .bin 与路径；
- `esptool` 封装：擦除、烧录、读取芯片信息（型号/MAC/Flash）；
- 进程级调用，捕获 stdout/stderr 供 AI 诊断。

**设备/串口层（Device & Serial）**
- 串口扫描（VID/PID + 芯片 ID 识别型号）、多设备并行管理；
- 串口监控：实时读取 + 手动发送，输出流供验证层消费。

**项目/存储层（Project & Storage）**
- 每项目一文件夹结构（见 3.4）；对话记录、各阶段日志、生成代码、编译产物持久化；
- 敏感数据（API Key 等）加密存储于应用配置区。

### 3.3 流水线状态机

```
Drafting ──(需求确认书生成)──> Confirmed ──(AI生成代码)──> Coding
   ↑                              │                         │
   │(用户改需求)                  │(用户确认)               │(代码就绪)
   │                              ↓                         ↓
   └────────────────────── Compiling <───(重试)────────────┘
                                 │
                      ┌──────────┴──────────┐
                  (编译失败,≤3次)        (编译成功)
                      │                      │
                      └─AI诊断修复→重编译    ↓
                                        FlashingConfirm
                                              │(用户确认)
                                              ↓
                                          Flashing <──(重试)──┐
                                              │               │
                                      ┌───────┴───────┐       │
                                  (烧录失败)     (烧录成功)    │
                                      │               │  AI诊断│
                                      └─重试──────────┤       │
                                              ↓       └───────┘
                                          Verifying <──(重试)──┐
                                              │               │
                                      ┌───────┴───────┐  AI诊断 │
                                  (验证失败)     (验证成功)      │
                                      │               │        │
                                      └─重试──────────┘────────┘
                                              │
                                      ┌───────┴───────┐
                                  (通过)          (超限)
                                      ↓               ↓
                                  Archived       Failed(转人工)
```

### 3.4 项目文件夹结构

```

├── project.json          # 项目元数据（型号/创建时间/状态/引脚黑名单快照）

```

## 4. 关键技术设计与约束

### 4.1 设备识别与型号映射
- **扫描**：枚举主机串口，读取 USB VID/PID；
- **识别**：优先用 `esptool flash-id`/`read-mac` 探测芯片型号（esptool v5 可自动识别 `--chip`）；辅以常见开发板的 VID/PID 映射表；
- **型号描述表（可扩展）**：每个型号一份配置，含 `chip` 参数、默认 Flash 偏移、引脚总数、特殊引脚（启动/电源/USB/禁用）等；v1 内置 S3、C3，后续追加；
- **手动修正**：识别结果在 UI 呈现，用户可改型号/串口。

### 4.2 引脚黑名单与危险代码告警
- **黑名单来源**：型号描述表内置（如 S3 的 GPIO0/45/46 启动相关、USB D-/D+ 等）+ 用户自定义；
- **校验时机**：代码生成后、烧录前各校验一次；
- **告警分级**：
  - *Error*：使用了黑名单引脚 → 阻断，必须修改；
  - *Warn*：潜在危险操作（关闭看门狗、引脚过载模式、修改启动配置等）→ 提示用户确认。
- **实现**：AI 生成代码时在 prompt 中注入黑名单；Rust 侧对生成代码做正则/AST 级引脚使用扫描复核。

### 4.3 LLM 适配与 Prompt 工程
- **统一接口**：`chat`/`generate_code`/`diagnose`/`judge` 四类调用，输入输出结构化；
- **供应商适配器**：OpenAI、Claude、国产（DeepSeek/智谱/通义等走 OpenAI 兼容接口优先）；
- **Prompt 模板**：按阶段维护（需求澄清/代码生成/错误诊断/结果判定），含型号引脚表、黑名单、示例库参考；
- **结构化输出**：需求确认书、验证判定使用 JSON 输出，便于编排器解析。

### 4.4 测试桩与验证协议
- **测试桩生成**：AI 在生成主代码时，同时生成测试桩代码，按约定输出格式：
  - `TEST:START <case_name>` / `TEST:PASS <case_name>` / `TEST:FAIL <case_name> <reason>` / `TEST:END`；
- **验证执行**：烧录后串口监控捕获输出，编排器提取测试桩标记；
- **AI 判定**：将测试桩输出 + 需求确认书的预期行为交给 AI，AI 输出结构化判定（通过/失败/原因）；
- **双板自测场景**（仅 Talk2ESP 自身开发用）：主从两套代码分别烧录两板，交叉读串口验证，用于验证 Talk2ESP 自身能力，不暴露给终端用户。

### 4.5 编译与烧录细节
- **编译**：`arduino-cli compile --fqbn <board>`，board 由型号描述表映射（如 S3 → `esp32:esp32:esp32s3`）；
- **核心包管理**：首次使用自动 `arduino-cli core install esp32:esp32`，版本固定可配置；
- **烧录**：`esptool --chip <chip> -p <port> -b 460800 write-flash <offset> <bin>`，offset 优先取 arduino-cli 编译输出；
- **错误捕获**：进程 stderr 完整捕获，常见错误（Failed to connect/Wrong boot mode/MD5 mismatch）有本地知识库辅助 AI 诊断（参考 esptool 资料库 `06_troubleshooting_kb.md`）。

### 4.6 安全与隐私
- **API Key 加密存储**：使用系统密钥库（Windows Credential Manager / macOS Keychain / Linux Secret Service）或应用级加密；
- **数据流向**：仅需求文本与生成代码经云端 LLM；串口数据、本地文件不外传；
- **烧录前确认**：默认开启，显示型号/串口/代码摘要；全自动模式可配置关闭但需用户显式同意。

### 4.7 技术约束
- **平台**：v1 优先 Windows（与测试环境一致），架构上预留 macOS/Linux（Tauri 跨平台特性）；
- **依赖体积**：内置 arduino-cli + esptool，目标安装包尽量精简；
- **esptool 资料库**：`esptool_esp32_research_pack/` 为只读参考资料，不入产品依赖，写入 `.gitignore`。

## 5. v1 范围、扩展点、验收标准

### 5.1 v1 功能清单（MVP）

**P0（必须）**
1. 设备自动扫描 + 型号识别（S3/C3）+ 手动修正 + 多设备并行；
2. AI 多轮对话澄清需求 + 生成需求确认书（JSON）+ 用户确认；
3. AI 生成 Arduino 代码 + 测试桩代码（含引脚黑名单校验、危险操作告警）；
4. arduino-cli 编译（内置，自动管理核心包）+ 失败 AI 诊断重试（≤3 次）；
5. esptool 烧录 + 烧录前确认 + 失败重试（≤3 次）；
6. 串口监控（可读可发）+ 测试桩验证 + AI 判定 + 失败重试（≤3 次）；
7. 项目文件夹持久化（代码/对话/各阶段日志）+ 导入导出；
8. 设置（LLM 供应商/Key、自动化模式、引脚黑名单）；
9. LLM 适配：OpenAI + Claude + 至少 1 个国产模型。

**P1（应做）**
10. 内置示例库（LED/按键/I2C 读传感器/SPI/PWM 调光/串口通信等）；
11. esptool 故障本地知识库辅助诊断；
12. 离线降级（查看历史项目 + 手动烧录，无 AI 对话）。

**P2（v1 不做，后续迭代）**
- ESP-IDF 框架支持、更多型号（S2/C6/H2 等）、示波器/波形可视化、本地大模型、Web 端。

### 5.2 扩展点设计

| 扩展点 | 机制 | v1 状态 |
|---|---|---|
| 芯片型号 | 型号描述表（chip/引脚/Flash 偏移/特殊引脚）配置驱动 | 内置 S3/C3 |
| LLM 供应商 | 适配器模式 + 统一接口 | OpenAI/Claude/国产 |
| 外设能力 | 直接生成原生 Arduino 代码，无需新抽象 | 依赖 AI + 示例库 |
| 编译框架 | 工具链层抽象（当前 arduino-cli） | 单实现 |
| 自动化模式 | 编排器配置项 | 全自动/分步确认 |

### 5.3 验收标准（v1）

**功能验收（以两块 S3 互连自测环境验证）**
1. 接入开发板，Talk2ESP 能自动识别两块 S3 的串口与型号；
2. 输入需求（如「GPIO1 输出方波，GPIO2 读取并回显串口」），经对话生成需求确认书；
3. 确认后自动生成代码 + 测试桩，编译通过；
4. 烧录前确认 → 烧录成功 → 串口监控显示测试桩输出 `TEST:PASS`；
5. AI 判定通过，项目归档；
6. 人为制造编译错误（如改错引脚），AI 能诊断修复并重试成功（≤3 次）；
7. 切换 LLM 供应商，流程仍可跑通。

**非功能验收**
- 安装包可在干净 Windows 环境运行，无需用户手动装 arduino-cli/esptool；
- API Key 加密存储，明文不出现在配置文件；
- 全流程日志完整可查；
- 引脚黑名单生效：生成使用 GPIO0 启动引脚的代码会被阻断告警。

### 5.4 风险与对策

| 风险 | 对策 |
|---|---|
| AI 生成代码质量不稳 | 示例库参考 + 测试桩验证 + 重试机制 |
| esptool 烧录失败率（驱动/波特率） | 本地故障知识库 + 自动降波特率重试 |
| LLM 供应商接口差异 | 适配器统一抽象 + OpenAI 兼容接口优先 |
| arduino-cli 核心包体积大 | 首次按需下载 + 版本固定 + 缓存复用 |
| 多设备串口冲突 | 串口占用锁 + 设备状态机 |

## 6. 附录：关键技术决策记录

| 决策项 | 选择 | 理由 |
|---|---|---|
| 产品形态 | 桌面应用 | 本地直接操作串口与 esptool，离线可用，对话体验好 |
| 桌面技术栈 | Tauri（Rust + Web） | 体积小、性能好、安全，契合轻量化理念 |
| 开发框架 | Arduino + arduino-cli | API 简单、库丰富、训练语料多、编译轻量 |
| AI 能力来源 | 云端 API，多供应商可切换 | 能力强，首批 OpenAI/Claude/国产 |
| 外设代码 | 直接生成 Arduino 原生代码 | 简单直接，无需维护额外抽象层 |
| 核心架构 | 流水线编排式（方案 A） | 流程显式可控、可追溯、安全门禁有确定落点 |
| 闭环验证 | AI 生成测试桩代码 + AI 读串口判定 | 可控、可追溯，避免 AI 自由理解误判 |
| 失败处理 | 自动重试上限 3 次 | 平衡全自动与可控，避免死循环 |
| 设备管理 | 自动扫描识别 + 手动修正 + 多设备并行 | 体验好且可控，支持双板自测 |
| 双板测试环境 | 仅用于 Talk2ESP 自身开发自测 | 不作为产品功能，避免增加用户门槛 |
